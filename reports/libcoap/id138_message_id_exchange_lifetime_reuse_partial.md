# Sent Message ID Reuse Is Not Guarded by a Full EXCHANGE_LIFETIME History

## Summary

libcoap randomizes the initial Message ID for UDP/DTLS sessions and increments it for each newly generated message. That is useful and matches the RFC implementation note for simple deployments.

The remaining gap is high-rate or wraparound behavior. The reviewed code does not maintain a sent-Message-ID history for the full `EXCHANGE_LIFETIME`, and the only explicit duplicate guard found checks a delayed queue rather than all active or recently used Message IDs for the endpoint.

## Standard Requirement

CoAP standard: RFC 7252, Section 4.4, online text:

[https://www.rfc-editor.org/rfc/rfc7252#section-4.4](https://www.rfc-editor.org/rfc/rfc7252#section-4.4)

Relevant original English excerpts:

```text
The same Message ID MUST NOT be reused
```

```text
(in communicating with the same endpoint) within the EXCHANGE_LIFETIME.
```

```text
The Message ID is generated by the sender
```

```text
The same Message ID can be reused only after EXCHANGE_LIFETIME
```

```text
It is strongly recommended that the initial value of the variable
```

```text
be randomized
```

```text
This Message ID MUST be incremented by one for each message
```

```text
as long as the sending rate does not exceed one message per second
```

Taken together, RFC 7252 Section 4.4 says more than "start from a random value" or "usually change the counter":

- the sender generates the 16-bit Message ID for unreliable transports
- with the same endpoint, a previously used Message ID must not be reused before `EXCHANGE_LIFETIME` has passed
- randomized initialization and sequential increment are recommended implementation strategies, not a relaxation of the lifetime rule
- the simple increment-by-one strategy is only described as sufficient when the sending rate stays low enough that wraparound cannot cause reuse inside `EXCHANGE_LIFETIME`

So the normative requirement being checked here is lifetime-based non-reuse with the same endpoint, not merely "different from the immediately previous MID" or "not currently still sitting in one retransmission queue".

## Relevant Source Code

Source file: `libcoap-develop/src/coap_session.c`

The initial value is randomized for unreliable transports:

```c
/* Randomly initialize */
/* TCP/TLS have no notion of mid */
if (COAP_PROTO_NOT_RELIABLE(session->proto))
  coap_prng_lkd((unsigned char *)&session->tx_mid, sizeof(session->tx_mid));
coap_prng_lkd((unsigned char *)&session->tx_rtag, sizeof(session->tx_rtag));
```

New Message IDs are generated by incrementing the session counter:

```c
uint16_t
coap_new_message_id_lkd(coap_session_t *session) {
  coap_lock_check_locked();
  if (COAP_PROTO_NOT_RELIABLE(session->proto))
    return ++session->tx_mid;
  /* TCP/TLS have no notion of mid */
  return 0;
}
```

The explicit duplicate check found in the send-delay path only scans `session->delayqueue`:

```c
if (COAP_PROTO_NOT_RELIABLE(session->proto)) {
  coap_queue_t *q = NULL;
  /* Check same mid is not getting re-used in violation of RFC7252 */
  LL_FOREACH(session->delayqueue, q) {
    if (q->id == pdu->mid) {
      coap_log_err("** %s: mid=0x%04x: already in-use - dropped\n",
                   coap_session_str(session), pdu->mid);
      return COAP_INVALID_MID;
    }
  }
}
```

Source file: `libcoap-develop/include/coap3/coap_session_internal.h`

The library defines `EXCHANGE_LIFETIME`, but the reviewed send-side Message ID allocator does not use it to retain a history of recently used Message IDs:

```c
/*
 * The EXCHANGE_LIFETIME definition for the session (s).
 * RFC 7252, Section 4.8.2 Calculation of EXCHANGE_LIFETIME
 */
#define COAP_EXCHANGE_LIFETIME(s) \
  (COAP_MAX_TRANSMIT_SPAN(s) + (2 * COAP_DEFAULT_MAX_LATENCY) + \
   COAP_DEFAULT_PROCESSING_DELAY)
```

## Inconsistency Reason

The implemented strategy is sufficient for ordinary low-rate traffic, but it does not prove the normative lifetime guarantee under rapid Message ID wraparound.

The key distinction is:

- implemented: randomized start plus monotonic 16-bit increment
- implemented: collision check for delayed unsent messages
- not found: full sent-Message-ID history retained until `EXCHANGE_LIFETIME`

If a session sends enough CON/NON messages to wrap the 16-bit counter before the relevant lifetime expires, the reviewed allocator has no visible lifetime cache to prevent reuse.

## Recheck Result

This remains a real partial inconsistency.

The implementation satisfies the randomized-initial-value recommendation and a basic changing-value strategy. It does not demonstrate complete enforcement of the `EXCHANGE_LIFETIME` non-reuse rule.
