# libcoap NON Response Message ID Reuse

## Summary

libcoap implements the normal ACK/RST Message ID echo behavior, and it uses a fresh Message ID for many sender-originated CON/NON messages. However, the ordinary server path for an immediate response to a Non-confirmable request initializes the Non-confirmable response with the request Message ID.

This is a partial compliance issue for ID 152: the implemented behavior is correct for ACK/RST and piggybacked ACK responses, but it is not correct for a NON response, which is its own sender-generated message.

## Standard Reference

RFC 7252: Section 4.3 Message ID, Section 4.4 Message Correlation, and Section 5.2.3 Non-confirmable.

Relevant original English text:

```text
The Message ID is generated by the sender of a Confirmable or Non-confirmable message.
```

```text
The Acknowledgement or Reset message MUST echo the Message ID of the Confirmable message.
```

RFC 7252 Figure 22 illustrates the relevant NON request/response case:

```text
GET (T=NON, Code=0.01, MID=0x7d40)
2.05 Content (T=NON, Code=2.05, MID=0xad7d)
```

The exact numeric values in the figure are examples, so the issue is not that libcoap fails to use `0xad7d`. The issue is that a NON response is not an ACK or RST. It is a Non-confirmable message generated by the responder, so the responder should generate the response MID rather than echoing the request MID.

## Code Behavior

For an application response, libcoap creates the response PDU in `coap_net.c` from the request type:

```text
libcoap-develop/src/coap_net.c:3950
response = coap_pdu_init(pdu->type == COAP_MESSAGE_CON ?
                         COAP_MESSAGE_ACK : COAP_MESSAGE_NON,
                         0, pdu->mid, ...)
```

For a Confirmable request, this correctly creates an ACK response with the request MID. For a Non-confirmable request, it creates a NON response but still passes `pdu->mid`.

The async separate-response branch changes a CON request's response type to `COAP_MESSAGE_CON`, but this path does not assign a new MID for ordinary NON responses:

```text
libcoap-develop/src/coap_net.c:3961
if (async && pdu->type == COAP_MESSAGE_CON)
  response->type = COAP_MESSAGE_CON;
```

The UDP header encoder then writes the PDU's current MID:

```text
libcoap-develop/src/coap_pdu.c:1597
pdu->token[-2] = (uint8_t)(pdu->mid >> 8);
libcoap-develop/src/coap_pdu.c:1598
pdu->token[-1] = (uint8_t)(pdu->mid);
```

## Runtime Evidence

The test `repro_id152_non_response_mid.c` starts a local libcoap UDP endpoint with a basic GET resource, sends a raw NON GET with `MID=0x7d40`, and captures the UDP response.

Observed log:

```text
request_type=1 request_mid=0x7d40 response_type=1 response_code=0x45 response_mid=0x7d40 saw_request=1
ID152_CONFIRMED_PARTIAL: NON response reused request MID
```

The response type is NON and the response code is 2.05 Content, but the response MID equals the request MID.

## Decision

Implemented part:

```text
ACK/RST and piggybacked ACK responses echo the request MID.
Sender-originated messages elsewhere use libcoap's message-id allocation paths.
```

Missing part:

```text
An immediate NON response to a NON request should use a responder-generated Message ID instead of echoing the request MID.
```
