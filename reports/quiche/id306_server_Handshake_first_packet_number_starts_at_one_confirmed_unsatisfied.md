# Server Handshake First Packet Number Starts at One

## Summary

RFC 9000 requires the first Handshake packet sent by a server to use packet number 0 in the Handshake packet number space. In the reviewed quiche implementation, outgoing packet numbers are generated by a single `QuicPacketCreator` sequence whose default first value is 1. Switching the default encryption level to `ENCRYPTION_HANDSHAKE` does not reset the sending packet number to 0 for the Handshake packet number space.

## Standard Requirement

Standard: [RFC 9000 Section 17.2.4, Handshake Packet](https://www.rfc-editor.org/rfc/rfc9000.html#section-17.2.4)

```text
Handshake packets have their own packet number space.

The first Handshake packet sent by a server contains a packet number of 0.
```

Required behavior: when a server sends its first packet in the Handshake packet number space, the packet header must carry packet number 0.

## Implementation Behavior

The first outgoing packet number is derived from `FirstSendingPacketNumber()`, which returns 1. `QuicPacketCreator` stores only one current `packet_.packet_number`; if it has not created a packet yet, `NextSendingPacketNumber()` returns the framer's first sending packet number.

When the connection changes to `ENCRYPTION_HANDSHAKE`, `SetDefaultEncryptionLevel()` updates the encryption level and forwards that level to the packet creator. It does not reset `packet_.packet_number`, does not create a separate Handshake sending counter, and does not set the next Handshake packet number to 0.

The serialized packet header is then filled from `NextSendingPacketNumber()`, so the first packet generated by this sending sequence starts at 1, not 0.

## Inconsistency Reason

The RFC requirement is packet-number-space specific: the server's first Handshake packet must carry packet number 0. The reviewed quiche sending path is not packet-number-space specific for assigning outgoing packet numbers. It starts from the global first sending packet number 1 and increments from the last packet created by `QuicPacketCreator`.

Multiple packet number space support does not change this conclusion. The reviewed per-space state in the framer, sent packet manager, and unacked packet map is used for parsing, ACK/loss bookkeeping, and retransmission accounting; it does not feed a per-space sending counter into `QuicPacketCreator::NextSendingPacketNumber()`. Dispatcher-sent Initial ACK packets can also advance the connection packet creator to a later packet number, but they do not create a Handshake packet number 0.

Because switching to Handshake encryption does not reset or select a Handshake-specific sending packet number sequence, the implementation does not satisfy the RFC 9000 Section 17.2.4 requirement.

## Impact

A peer that strictly validates the first server Handshake packet number against RFC 9000 can observe packet number 1 or a later value instead of 0. This creates an interoperability and compliance risk for QUIC v1 Handshake packet processing.

## Fix Direction

The sending path should maintain packet numbers independently per RFC 9000 packet number space. For QUIC v1, the server's Handshake packet number space should initialize its first outgoing packet number to 0, and `QuicPacketCreator` should select and update the correct per-space counter when serializing Initial, Handshake, or Application Data packets.
